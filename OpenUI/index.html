OpenUI. 让模型别再写 JSON —— 一种为 UI 而生的流式小语言

当 AI 要「画」一个界面，最自然的做法是让它吐一段 JSON 组件树。但一旦界面需要状态、需要查数据、需要响应点击，JSON 就暴露出结构性缺陷：括号错一处，整份输出报废；一个下拉框要几十行嵌套对象。OpenUI 的答案是造一门像代码一样好写、像数据格式一样受限的语言——OpenUI Lang：每行一条 id = Component(args)，逐行流式渲染，比 JSON 省最多 67% token，并让运行时在模型退场后独立执行交互。

一分钟速览

如果只看一屏：OpenUI 是一套「声明式生成式 UI」标准与全栈框架。它赌的是——模型输出 UI 的正确形态不是 JSON，也不是完整编程语言，而是夹在中间的受限 DSL；界面应该被生成一次，然后像普通软件一样在本地跑起来，而不是每次点击都回炉给模型。

🧩 它是什么

Thesys 开源的生成式 UI 框架。核心是 OpenUI Lang：行式赋值 DSL；配套组件库（Zod schema 定义）、系统提示生成器、流式解析器、渲染器。MIT 协议，2024-12 建仓，现约 9,900 stars。

🎯 解决什么

让 LLM 生成的界面「可靠、便宜、可流式」。JSON 里每个父节点都要重复写 op/path/type/props/children，深层界面 token 成本翻 2–3 倍；且 JSON 没有「更小可回退单元」，一处括号错整屏报废。

⚙️ 核心机制

四件套闭环：组件库 → 系统提示 → 模型流式输出 Lang → 渲染器。允许前向引用，所以 root 先到、子节点后到，骨架屏可以立刻出现；每行一条语句 → 解析错误只损失一行。

🔁 生成 ≠ 执行

v0.5 加入 $state / Query / Mutation / @builtins。模型只生成一次「接线」，之后筛选、刷新、提交全部由运行时直接调工具完成，零 token、约 100ms。

📊 关键数字

Token：4,800 vs json-render 10,180（−52.8%），单场景最高 −67.1%。可靠性（官方博文口径）：结构有效 96.5% vs 95.7% vs 80.2%，1104 次运行里仅 1 次白屏（A2UI 35 次）。

⚠️ 必须警惕

基准是第一方自测；「白屏少」不等于「用户看不见错」（OpenUI 会以部分渲染替代白屏）。社区最大质疑：动态生成的「变色龙 UI」破坏肌肉记忆与可访问性。名字还和 W3C 的 OpenUI 社区组撞车。

01

出发点：一个「JSON 原教旨团队」的自我背叛

最有说服力的批评往往来自当事人。Thesys 在 2025 年 3 月上线了 C1——一个基于 JSON 组件树的生成式 UI SDK：50+ 组件、能渲染半成品流的解析器、真实生产流量。它工作得很好。然后团队想让它可交互，JSON 开始处处与他们为敌。

「JSON 是一个假装成语言的数据格式。当你需要一个能取数据、管状态、响应输入的 UI 时，这个区别就不再是理论问题。」 "JSON is a data format pretending to be a language. When you need a UI that can fetch data, manage state, and respond to user input, that distinction stops being theoretical."
——《Stop making AI write JSON》（Thesys Engineering，2026-04-10）

JSON 的三次「叛变」

① 数据被冻进输出里

"data": [120,150,180] 一旦被模型写出来就定格了。想换数据？回模型。想加筛选？回模型。每一次交互都是一次完整的 LLM 往返。

② 语言特性被「对象化」

一个三元表达式 a ? b : c 要写成 {"$cond":{...},"$then":x,"$else":y}；一个布尔表达式要嵌套三层的 $or/$and。模型把 token 花在括号与包装对象上，而不是界面设计上。

③ 结构错误会「污染全局」

JSON 是一个整体文档。第 12 行少一个 }，后面 50 行全部作废。而 OpenUI Lang 每行自包含、括号在本行闭合——解析错误只损失那一行，还能用 linter 式诊断精准修。

同一个 TODO 应用，两种写法：模型实际要生成的东西

更根本的账：把「取数据」交给模型是架构错误

Thesys 另一篇博文《Your LLM is not a query engine》算了一笔账：在工具调用（tool-calling）循环里，模型同时干两件事——理解意图（它擅长的）与搬数据（它极不擅长的）。而且成本随「交互次数」而非「问题难度」增长：

📈 历史累积

每轮都重发完整对话，其中包含之前所有工具结果。第 10 次筛选比第 1 次更贵，尽管操作完全相同。

📦 数据注入

500 行聚合结果序列化后约 1–2 万 token，且此后每一轮都躺在上下文里。等于用最贵的通道搬运数据。

🎲 查询重推导

查询每轮从零重写，都是新的采样。第 3 轮设的地区筛选，可能在第 7 轮静默丢失；而且用户读到的每个数字都被模型「重打过一遍」。

02

OpenUI Lang 解剖：夹在 JSON 与 JavaScript 之间的那块空地

团队反复强调一个定位：JSON 是假装成语言的数据格式，JavaScript 是能力过剩的语言，而生成式 UI 需要的恰好在中间——看起来像代码（LLM 对代码有海量预训练），但受限得像数据格式（没有逃逸出口，没有 while(true)，不能 import 你没装的库）。

2.1 语法：一行一条赋值

语言只有一种语句形态：identifier = Expression。参数是位置参数，按 Zod schema 的 key 顺序映射；允许省略尾部可选参数；允许前向引用。另外有两类特殊语句：状态声明 $name = default 与数据语句 name = Query(...) / Mutation(...)。

为什么「位置参数」很关键：它把组件签名从「键值对」压缩成「一串值」，每行省下的引号与键名，乘以无数次生成就是真金白银。但它也把 Zod key 顺序变成了 ABI——改 schema 顺序 = 改语言协议。这是设计与代价的两面。

2.2 内置函数：把「计算」留在运行时

DATA

@Count @Sum @Avg @Min @Max @First @Last @Filter @Sort @Round @Abs @Floor @Ceil

ITER

@Each(array, varName, template)

按行渲染，循环变量仅在内联可用——这是「模板即表达式」的极简版。

ACTION

@Run(ref) @Set($v,val) @Reset($v...) @ToAssistant(msg) @OpenUrl(url)

动作按序执行；@Run 失败则跳过后续步骤。

DATA IO

Query(tool, args, defaults, refreshSec)
Mutation(tool, args)

Query 载入即执行并在 $var 变化时自动重取；Mutation 只由 @Run 触发。

可搜索、可排序的表格 · 全部逻辑在客户端，零模型往返

2.3 增量编辑 = 重新赋值

用户说「加一个只显示未完成的筛选器」。模型不需要重发整个应用——各语言变量「后定义覆盖先定义」，所以它只重写改动的三行，未提及的语句原样保留。这就是 OpenUI 的编辑模型：没有 RFC 6902，没有 JSON Pointer 算术，没有「编辑模式选择」。

03

架构：四件套闭环，与「生成 / 执行」的切割

OpenUI 的核心循环只有五步，但每一步都能替换：组件库用你的设计系统，提示由 schema 自动生成，解析器把流变成带类型的元素树，渲染器把树映射到你的组件。语言与渲染器不依赖任何模型厂商、聊天库或托管服务。

图 1 · OpenUI 核心循环：组件库驱动提示，提示驱动生成，渲染器承接执行

解析流水线：六段，以及一个反直觉的工程结论

解析器要在每个流式分片上运行，延迟极度敏感。它的流水线是：

autocloser → lexer → splitter → parser → resolver → mapper → ParseResult

其中 autocloser 负责把「流到一半」的文本补成语法合法（补引号与括号），resolver 负责内联变量引用（即前向引用的「提升」）并检测循环引用；splitter 把 token 流切成 id = expr 语句。因为每个语句以深度为 0 的换行结束，所以已完成的语句是不可变的，可以缓存 AST，只重新解析末尾那条未完成的。这让整条流的解析从 O(N²) 降到 O(N)。

工程故事 · 他们把 Rust/WASM 解析器重写成了 TypeScript，然后快了 3 倍。原因不是 Rust 不快，而是 WASM ↔ JS 边界的税：每次调用都要把字符串拷进 WASM 线性内存、把结果序列化成 JSON 字符串、再拷回来给 V8 反序列化。他们还试过 serde-wasm-bindgen 直接返回 JS 对象，结果慢了 9–29%——逐字段具象化反而制造了成百上千次细粒度跨界。
方案单次调用（µs）整条流总成本备注
Rust/WASM + JSON 往返20–61基线每次调用都付拷贝税
Rust/WASM + serde-wasm-bindgen22–79+9–29% 更慢内部跨界次数更多

组件如何定义（TypeScript / Zod）

import { defineComponent, createLibrary } from "@openuidev/react-lang";
import { z } from "zod/v4";

const StatCard = defineComponent({
  name: "StatCard",
  description: "显示一个指标标签与数值。",
  props: z.object({ label: z.string(), value: z.string() }),  // key 顺序 = 位置参数顺序
  component: ({ props }) => (<div><strong>{props.label}</strong><div>{props.value}</div></div>),
});

export const myLibrary = createLibrary({
  root: "StatCard",              // 提示会强制模型以 root = StatCard(...) 开头
  components: [StatCard],
  componentGroups: [
    { name: "Charts", components: ["BarChart", "LineChart"],
      notes: ["- 对比用 BarChart，趋势用 LineChart。"] },
  ],
});

提示生成器会把 schema 变成组件签名、语言规则、示例与流式指令。root 字段有双重作用：约束模型输出形态，同时让 root 语句排在流的最前面，界面外壳可以立刻渲染。官方给出的「给 LLM 写组件」最佳实践：schema 保持扁平、必需参数在前、组件命名要有区分度、库越小越好、用 .ref 组合而非深层嵌套、用 componentGroups 分组并附上使用提示。

v0.1 → v0.5：从「静态生成」到「自带状态的应用」

v0.1
静态 UI 生成

只有组件树。像一段可渲染的数据，交互全靠宿主自己接。

v0.5 (最新)
响应式状态 · 查询 · 变更 · 内置函数

引入 $variables 双向绑定、Query/Mutation 数据声明、@builtins 计算与 Action 组合。自此「模型生成接线，运行时执行交互」成立。

提示特性开关
toolCalls / bindings / editMode / inlineMode

提示按开关裁剪：是否教模型用工具、是否启用 $var、是否启用增量编辑、是否允许模型「只回答文字不画 UI」。bindings 默认跟随 toolCalls。

为什么 JSON-Render 比预想更重？它为每个元素生成一条 {"op":"add","path":"/elements/id","value":{...}}，op / path / value / type / props / children 这些键在每个节点都重复一遍。界面越深，结构重复累积越严重——在七个场景里最高达到 OpenUI Lang 的 3 倍 token。

6.1 失败不是随机噪声，而是有固定形状

Thesys 公布了一周真实生产流量的失败归因。值得注意的是：失败是结构性的，不是语义性的——模型自上而下规划界面，先列出一个 section 的子节点再定义它们，长输出里它可能忘了把成品 section 挂回 root，或者在一张表的最后几行耗尽预算。

7.1 为什么选扩散语言模型

自回归模型逐 token 生成，瓶颈在显存带宽。DiffusionGemma 一次写一个 256 token 的块，从噪声出发、确定一个就提交一个；Google 报告在单张 H100 上超过 1000 tok/s，RTX 5090 上超过 700。这正好对上 Thesys 的硬约束：界面要在一秒内生成、要可靠到能当软件用、要小到能本地跑。

7.2 「跷跷板」问题：两类错误此消彼长

训练分两阶段。第一阶段监督微调（约 700 个由更大模型写的 Lang 示例，跳 7 个组件库，A100 上 LoRA），基准从 13.0% 升到 28.8%。但出现了一个反复出现的现象：schema 错误与 wiring 错误像跷跷板，一次训练只能压下一头。

监督微调阶段的「跷跷板」
同一组件库上连续三次训练运行的错误计数

更糟的是模型变慢了：同一批 20 条 brief，生成时间从 1.6s 涨到 4.3s。原因很有意思——基座快是因为输出短而通用（平均 22 token/语句）；微调后它写出真实的名称与数值（平均 32 token/语句），且需要约两倍的去噪步数才能提交每个 token。他们教会了模型写出更有用的界面，却丢掉了 DiffusionGemma 最初的意义。

7.3 转折点：把解析器当作奖励（自蒸馏）

关键洞察是：OpenUI Lang 有可验证的奖励。解析器能判断结构是否有效，并在失败时指出确切的 schema 或 wiring 错误。于是模型可以当自己的老师：生成程序 → 用解析器筛选 → 近似正确的走一次「最小修复」→ 判官检查是否契合 brief → 通过者成为下一轮训练集。每轮 500 步，A100 上约 1–2 小时。

🥊 OpenUI 的真实优势

① 单位 token 效率与 TTFR；② 每行自包含 → 失败是局部的、可修复的；③ 语言内建数据获取，不需要自己拼 hooks 与状态库；④ 官方运行时覆盖 React/Vue/Svelte/Angular，且 MIT。评测里 json-render 的失分有压倒性单一原因：959 个评分错误中 929 个是引用图失败（悬空或孤儿 element id）——扁平补丁注册表把每个父子关系都变成必须全局一致的字符串 id。

🧊 json-render / A2UI 的反击点

json-render 的差异性是渲染面广度：同一份 spec 可产出 Web、邮件、PDF、终端，这对「一次写、多处渲染」的产品很关键。A2UI 的差异性是目录协商握手与原生渲染器（Flutter、Angular、Lit），对需要原生 widget 的移动/桌面场景更合适。OpenUI 目前赢在 Web 内的效率与可靠性，不赢在所有渲染目标的覆盖度。

10.1 需要谨慎对待的四个点

⚠️ 基准是「第一方自测」

作者在基准脚注中主动披露：「我们造了 OpenUI Lang，所以请把它读作第一方基准，包括 70 组件目录来自我们自己的公开库这一事实。」数据、提示、原始输出都提交在 generative-ui-bench 仓库供独立复评——这比多数厂商诚实，但仍不是第三方评测。

⚠️ 「白屏少」≠「用户没看到错」

官方自己指出：逐行失败让 OpenUI 用部分渲染替代白屏，而「部分错」往往比白屏更难被察觉。所以他们把结构有效率与白屏率分开报告。任何把这解读为「OpenUI 不会出错」的说法都是过度推论。

⚠️ 新 DSL vs 预训练优势

社区质疑：引入全新 DSL 与 LLM 的预训练分布相悖（训练数据里有海量 HTML/React/JSON，几乎没有 OpenUI Lang）。官方的回答是双管齐下——用系统提示 + 丰富 few-shot 引导通用模型，以及用微调模型（OUI-1）把 DSL 变成母语。基准显示通用前沿模型在 Lang 上的结构有效率与 JSON 系基本持平，算是部分回答了这个问题。

⚠️ 生态与工程成熟度

版本号仍在 0.x（react-ui 0.16.3、lang-core 0.3.0），出现过 peer 依赖窗口不一致、流式解析器与主解析器在重复 id 与多行三元表达式上的行为差异等 issue（如 #821、#1127）。releases 里 devin-ai-integration 机器贡献者频繁出现——自动化程度高，但也意味着 API 仍在快速变动。

还有一个不太浪漫但重要的细节：仓库 README 顶部专门声明——「OpenUI 没有官方加密货币、代币或币。任何使用 OpenUI 名称的资产都与本项目无关。」一个开源框架需要在首页辟谣山寨币，本身就是 2026 年的时代注脚。

10.2 那么，它到底适合谁？

场景建议理由
对话式数据分析 / 可筛选看板首选 OpenUI模型生成一次接线，之后筛选刷新完全不烧 token、不走模型——这正是它设计的甜点。
产品内嵌、强设计系统的副驾驶首选 OpenUI组件由你的 Zod schema 与设计系统定义，模型不能越界生成任意样式。
同一份 spec 要渲染成 Web + PDF + 邮件 + 终端考虑 json-render它的渲染面广度仍是最强的护城河。
需要原生 widget（Flutter / iOS / Android）考虑 A2UI目录协商与原生渲染器是它的主场。
一次性、探索性、创造性的可视化开放式 HTML（沙箱内）没有目录能装下它。官方推荐的做法是把 GeneratedView 这样的沙箱组件注册进声明式目录——按子树支付开放式生成的成本。
在别人的宿主里（ChatGPT/Claude）出现MCP-Apps这是传输层问题，与生成格式正交。

启示：这份 repo 真正值得带走的三件事

① 约束是一种接口设计

「没人用 Python 去查数据库——不是因为它不够强，而是因为 SQL 让契约变得明确。」OpenUI Lang 的赌注是：给 LLM 一个没有逃逸出口的表示，比给它一门通用语言更可靠。这可以推广到任何「模型 → 结构化系统」的接口设计。

② 让模型退场的架构，往往更便宜也更准

把「理解意图」与「搬运数据」拆开，是这个 repo 最有普适价值的一课：模型生成声明，运行时执行。用户的每个数字都来自数据库，而不是被模型复述一遍。这条原则与具体语言无关。

③ 可验证性是可训练性的前提

OUI-1 的故事本质是：因为 Lang 每行自包含、解析器能给出精确诊断，所以「解析器」可以直接当奖励信号，把 13.0% 的基座拉到 71.7%。先设计出可判定对错的输出格式，模型才可能靠自我博弈变强。

如果生成式 UI 的未来是「模型只在需要思考时出场」，
那么 OpenUI 贡献的不是一门语言，
而是一份关于「模型与运行时如何分工」的工程契约。
