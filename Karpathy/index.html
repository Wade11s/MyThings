We'll be spending a lot more time trying to understand the outputs of language models. A few thoughts, tips & tricks: Writing. Something I've had success with: Ask your LLM to explain something in ASD-STE100, it's a controlled language specification originally developed for aerospace maintenance documentation. LLMs [are] well-versed in this language and it comes with heavy constraints on clean writing style that I often find a lot more readable. Sometimes I've tried to soften it a bit e.g. ask for "80% of the way to ASD-STE100" because the spec is quite stringent. But even better: Diagrams / images. Instead of writing, ask your LLM to create a diagram. These can be a lot easier to process, parse, and understand. But even better: Web pages. Ask for output "in HTML" to get a beautiful, interactive webpage. LLMs are getting really good at frontend and can create beautiful experiences, animations, etc. But even better: Explainer videos. The output format I am most bullish on is fully custom / bespoke explainer videos generated on any arbitrary topic. Experiment with things like "Create a 3b1b style video explainer on X. Use my ElevenLabs API key for audio narration". (you'd need an API key for the latter or you can ask your LLM to find you decent free alternatives that use your local compute). This is actually starting to work! In summary: - As LLMs get better, they will do more and more of the legwork autonomously, and a lot more of our work will rise up the abstractions into oversight and understanding. - Luckily, LLMs can help here too because as intelligence and code are increasingly abundant, you can ask for large, custom, discardable software artifacts (e.g. web apps, video explainers) that would have never made sense to create before. Push the boundaries here and you'll be surprised.

② 图解 / 图片。不要写，改成让模型画一张图。图更容易被处理、解析和理解。但更好的方式是：

③ 网页。要求「以 HTML 输出」，你会得到一个漂亮、可交互的网页。模型的前端能力越来越强，能做出很美的体验和动画。但更好的方式是：

· 随着模型变强，它们会自主完成越来越多的粗活，我们的工作会整体上移到「监督与理解」的抽象层。

02

核心论点：这是一条关于「抽象层迁移」的判断

这条长推表面上在讲「怎么让 AI 讲得更好懂」，但它真正的骨架是一个关于工作性质变化的论断。输出格式阶梯只是这个论断的操作化落地。

一句话概括：当「生成」变得廉价之后，瓶颈就从生产转移到了理解。而理解一个东西的最短路径，不是读更多字，而是让模型换一个更接近人类认知的形式来输出。

三层结构

第 1 层 · 现象

格式比措辞更影响理解

同样的知识量，模型用一段话讲、用一张图讲、用一个网页讲、用一支视频讲，你吸收它的速度差出一个量级。Karpathy 反复实测后，把这条经验固化成了阶梯。

第 2 层 · 机制

抽象层整体上移

「As LLMs get better, they will do more and more of the legwork autonomously」——粗活（legwork）交给模型，人的工作上移到 oversight（监督）与 understanding（理解）。这是他对「AI 会不会取代程序员」这个问题的替代性回答：取代的不是人，是那一层具体动作。

第 3 层 · 机会

「用完即弃」的定制产物

因为智能和代码变便宜了，过去因为「不划算」而被放弃的需求（一个专属于自己的讲解视频、一张只为自己定制的图）现在边际成本接近零。他把这类产物称为 discardable software artifacts。

为什么「discardable（用完即弃）」这个词是关键

过去 AI 生成代码的最大心理障碍是「我得为它负责」：要审、要维护、要长期共存于代码库里。这让很多人宁可自己写。「用完即弃」重新定义了成本结构——

维度传统做法用完即弃的产物
维护成本需要长期维护，纳入代码评审流程用完就删，不进主干，不需要长期 owner
质量门槛必须一次写对，否则污染系统允许 60 分，因为重做成本极低
触发条件「我需要这个功能」「我有点想理解一下这件事」——好奇本身就够了
产出形态一份规范文档一个可交互网页 / 一支 3 分钟动画

这条长推真正的杠杆在这里：它把「学习/理解」这件事的成本，压缩到了接近零。你想搞懂 TCP 拥塞控制？以前要么读三章论文，要么花钱找教程；现在一句话生成一支为你量身定制的动画。

03

四级输出格式阶梯（可交互）

这是原推最核心、也最可直接复用的部分。每一级都比上一级更贵、更难自检、但理解密度更高。点击任意一级，看它的提示词写法、理由和示例。

L1受控语言文字同一段话，可读性大幅提升
L2图解 / 图片「不写，画出来」——更容易被解析
L3网页（HTML）可交互、可动画、可分享的单文件产物
L4定制讲解视频Karpathy 最看好的终局形态

L1 · 受控语言（Controlled Language）

为什么这一步有效：模型的默认输出是「通用互联网英语」——大量被动句、从句嵌套、修辞性连接词。对 experts 是可读的，对快速吸收是低效的。套一层硬约束，等于强行把模型从「写得好」切换到「说得准」。

提示词模板
# 严格版
用 ASD-STE100 解释 <主题>。

# 实战更常用（Karpathy 推荐）
用「80% 的 ASD-STE100」解释 <主题>。
✕ 默认输出风格

「在当今的数据传输场景中，拥塞控制机制扮演着至关重要的角色，它的设计往往涉及到对网络状况的一个综合考量，而不仅仅是单一的带宽指标……」

✓ 受控语言风格

「拥塞控制决定发送速率。发送端不能只看着带宽。带宽和时延会共同改变网络容量。丢包是拥塞的信号。算法据此减小发送速率。」

右侧为示意改写，用于呈现 ASD-STE100 的典型特征（一句一义、主动语态、避免名词化、只用受控词表），非模型实测输出。

L2 · 图解

为什么这一步有效：人眼对空间结构的处理是并行的，对线性文本是串行的。一张流程图能同时呈现分支、循环、时序，而文字必须逐句重建这些结构。Karpathy 的措辞是图「更容易被处理、解析和理解」（process, parse, understand）——注意他把这三个动词都给了「读图」。

提示词模板
不要写文字。画一张图解释 <主题>。

# 更强的版本（自包含，可直接打开）
画一张 Mermaid 图解释 <主题>。
要求：节点不超过 12 个，标注主干路径，
用不同形状区分「数据 / 控制 / 状态」。

实操建议：让模型输出 Mermaid 或 SVG 而不是位图——前者是文本，可以被你二次编辑、可以 diff、可以塞进任何 Markdown 渲染器。位图只能看，不能改。

L3 · 网页（HTML 输出）

为什么这一步有效：这是整条阶梯里性价比的拐点。你不需要任何工具链，只要一个 .html 文件，双击就能看；它同时承载了文字、图形、动效和交互——相当于把 L1~L2 的收益打包，同时获得了 L1 的可搜索性和 L4 的表现力。

提示词模板
用 HTML 输出一篇讲解 <主题> 的网页。

要求：
- 单文件，CSS/JS 全部内联，零外部依赖
- 暖色调、衬线标题，风格参考一个你认可的页面
- 包含 3 个可折叠的细节区
- 关键流程用内联 SVG 画出来
- 结尾留 3 个「你现在应该能回答」的自测问题

你正在看的这一页，本身就是 L3 的产物。它满足上面几乎每一条约束：单文件、内联样式与脚本、无外部字体和图片、可离线双击打开。这就是他说的「a beautiful, interactive webpage」的实际形态。

L4 · 定制讲解视频（Karpathy 最看好）

为什么这一步是终局：前三级本质上都还是「你自己在读」。视频是唯一一个「你什么都不用做，信息自己流进来」的形式——注意力成本最低。而且它可以完全按你的认知习惯定制：语速、深度、类比、举例偏好。

提示词模板（原推原话的中文化）
为 <主题> 制作一支 3b1b 风格的讲解视频。
用我的 ElevenLabs API key 做语音旁白。

# 没有 API key 时的变体
为 <主题> 制作一支 3b1b 风格的讲解视频，
用我本地算力能跑的免费 TTS 方案做旁白
（先帮我比较几个方案再选定一个）。

如何理解「3b1b 风格」

3b1b 即 3Blue1Brown（Grant Sanderson），以「手写感的数学动画 + 逐步揭示 + 旁白与动画严格同步」著称。让模型模仿这个风格，实际上是在指定一套具体的视听规范：极简配色、大字号公式、镜头缓慢推近、每一步只引入一个新概念、旁白不重复屏幕上已有的字。

注意成本结构：L4 已经不是「一次问答」的量级了。Karpathy 提到类似量级的任务——在 2026 年 8 月 2 日的另一条推文里，他让 Opus 5 用 100 万 token 预算（≈10 美元）跑约 2 小时，写了 5500 行代码来程序化渲染《指环王》开篇段落。推特那句「This is actually starting to work!」的分量，就来自这个量级的实证。

04

重点拆解：ASD-STE100 到底是什么

这是整条推文里最「反直觉」的一招——用一套航空航天工业标准来改善 LLM 的输出质量。为什么它有效，值得单独讲。

是什么

Simplified Technical English（STE），一套受控自然语言。1980 年代由欧洲航空工业协会（AECMA）应欧洲航空业需求开发，起因很务实：同一个飞机部件的维修手册要发给世界各地的技师，很多人的母语不是英语，翻译损耗导致误操作。

现行版本（2025 年 1 月发布）包含 53 条写作规则和约 900 个受控词的词表。

约束了什么

· 一句话只表达一个动作
· 强制主动语态、禁止名词化（用 "install" 而非 "installation"）
· 只能使用词表内的受控动词
· 禁用缩略语、禁用大部分非受控连接词
· 固定冠词、时态、数的使用规则

为什么这套标准会「意外地」适合 LLM

Karpathy 说的是「LLMs are well-versed in this language」——模型对这套规范的熟悉度非常高，因为它的语料里存在大量严格遵循该标准的航空/军工技术文档。约束越硬，模型的输出空间越小，「跑偏」的概率就越低。

从工程角度看，这是把提示工程问题转化成了格式选择问题。你不需要写长 prompt 描述你想要的文风，只要指定一个已有的、有共识的规范。这是很典型的 Karpathy 式思路：不要发明新框架，去挂到一个已被验证的标准上。

「80% 的 ASD-STE100」——这个细节是整条推文里最实用的部分

完整规范「quite stringent」（相当严格），对非技术话题会显得过于生硬。Karpathy 的解法是给出一个可调的中间档。这是一个很小但很关键的设计：把「格式」变成一个连续量而不是开关。

可交互：格式强度滑块

拖动滑块，看同一个请求在「默认文风 → 60% → 80% → 100% STE」下的表述差异。这是对 Karpathy 那个「80%」技巧的直观演示。

05

L3 为什么是拐点：HTML vs Markdown

Karpathy 说「Ask for output in HTML」，这句话在 2026 年上半年恰好撞上了一场行业辩论：AI 的默认输出格式该不该继续是 Markdown？

辩论的背景是：Anthropic 内部有人主张 Claude 应该停止用 Markdown 回答用户，改用 HTML。理由包括信息密度（Markdown 是一行一句话的线性流，HTML 可以并排、可以折叠、可以用视觉层级）、可分享性（一个文件就是一个完整的东西）、以及交互性。这与 Karpathy 这条推文的立场高度一致——他在 X 上给的是同一方向的经验证据。

维度Markdown 输出HTML 单文件输出
信息密度线性，一句一行可多栏、可折叠、可分层
可交互基本无可做动画、模拟器、图表
可编辑极强（纯文本，可 diff）强（语义标签清晰）
二次加工贴进任何笔记系统需要浏览器才能看
复用价值高（文本是通用原料）高（可视化产物本身即交付物）

不要二选一。更实用的做法是按用途分流：需要被引用、被 diff、被喂给下一个模型的对话 → 要 Markdown；需要被理解、被演示、被自己反复回看的知识 → 要 HTML。Karpathy 说的「更可读」是针对人作为读者这一角色而言的。

可直接复用的 HTML 提示词骨架

用 HTML 输出一篇讲解 <主题> 的网页，要求：

1. 单文件   —— CSS/JS 全部内联，零外部依赖，双击可开
2. 有视觉层级 —— 衬线标题、暖色系、留白充足
3. 有可交互   —— 至少 3 个可折叠区 / 一张内联 SVG 图 / 一个交互演示
4. 有检索性   —— 结构用语义标签，目录可跳转
5. 有验证点   —— 结尾 3 个自测问题，附折叠答案
6. 有出处     —— 标注原始来源链接与抓取时间

第 6 条来自本仓库的实践。一个 AI 生成的网页最大的隐患是「看起来很权威但内容是编的」。要求它标注来源与时间戳，成本几乎为零，却能立刻区分「真调研」和「幻觉」。

06

L4 的实战配方：怎么把「3b1b 视频」真的跑通

原推只给了一句话指令，实际上执行链条更长。下面是一个可复用的完整配方，按环节拆开。

执行链条

STEP 1

脚本

先要一份逐镜头脚本：每个镜头画面是什么、旁白说什么、停留几秒。确认后再动手。

STEP 2

配音

用 ElevenLabs 生成旁白音频；无 key 时改用本地 TTS（如 Kokoro / Piper / macOS `say`）。

STEP 3

画面

让模型写程序化动画（Manim / Remotion / ECharts 序列帧），而非生成静态图再硬凑。

STEP 4

合成

用 ffmpeg 把音频与画面按时间轴对齐，输出 mp4。旁白长度反过来决定动画节奏。

完整提示词（工程化版本）

为 <主题> 制作一支 3b1b 风格的讲解视频，交付一份可运行的项目。

# 风格规范
- 极简配色，深色背景，单一强调色
- 公式分步揭示，每一步只引入一个新概念
- 旁白不重复屏幕上已有的文字
- 目标时长 2–3 分钟

# 交付物
1. shots.json   —— 逐镜头描述（画面 / 旁白 / 时长）
2. narration.txt —— 完整旁白稿
3. build.py 或 build.ts —— 程序化生成动画的脚本
4. Makefile     —— 一条命令出片
5. README.md    —— 如何换主题 / 换配色 / 换语言

# 约束
- 先输出 shots.json 让我确认，再继续
- 旁白用我的 ElevenLabs API key；没有就换本地 TTS 并说明

为什么必须先确认脚本：视频是所有格式里返工成本最高的（配音和动画都得重做）。这就是 Karpathy 说的 L4「even better」的另一面——你得到的理解密度更高，但你的审核机制必须相应升级，从「读一遍」变成「读脚本 + 看片」。

07

深度分析：这条推文在论证什么，它没说什么

把上面所有操作化细节抽掉，看这条推文隐含的判断结构。

论点 A：稀缺性发生了转移

过去稀缺的是「实现」——把一个想法变成可运行的东西需要时间和技能，所以不是每个想法都值得实现。Karpathy 说「as intelligence and code are increasingly abundant」，意思是实现正在变成近乎免费的东西。

一旦实现变便宜，稀缺的就转移到了「知道该实现什么」和「判断实现得对不对」。这就是「工作上移到 oversight and understanding」的全部含义。输出格式阶梯，就是为这层新工作配备的工具。

论点 B：这是一个关于「注意力」的经济学判断

阶梯的排序逻辑值得单独拆开看。Karpathy 不是随便列了个清单，四级之间是严格递进的：

级别输出物它替你省掉了什么它的成本
L1受控语言文字省掉「读懂」的额外算力几乎为零
L2图解省掉「在脑中重建结构」的串行工作需渲染/看图
L3网页省掉「自己做演示」的时间需浏览器
L4视频省掉「你自己读」这件事本身算力 + 时间 + 审核成本

递进的方向是「作者的呈现负担」越来越重，「读者的参与负担」越来越轻。到了 L4，读者的参与负担降到最低——你只需要看。这就是他说的「This is actually starting to work!」的真实含义。

论点 C：他没说的三件事

① 审核成本没有消失

原推只谈「理解效率」，没谈「验证成本」。L4 尤其危险：你很难在两分钟的视频里发现第 47 秒的一个事实错误。Karpathy 自己在另一条推文里承认过这个软肋——模型无法高效地自我审计，因为它不能像人一样「玩」自己的作品。

② 他是「最不能用 AI 的人」在说话

一位在多家前沿实验室工作过的研究者，他的日常信息流天然就是被 LLM 高度优化过的。他说的「更可读」是相对于专家读者而言。零基础读者从这套方法里能拿到的收益，比例上应该更高，但盲区也更大——他没覆盖非技术、非英语、无图形直觉的人群。

③ 阶梯顶端没有闭环

阶梯止于「生成」。但如果没有 L1 那种可搜索、可引用、可 diff 的纯文本兜底，生成出来的一堆视频和网页会变成新的信息孤岛。他给的是产出侧的效率方案，没给沉淀与检索的方案。

放到他自己的历史脉络里看

这条推文和 Karpathy 过去两年的几个动作是同一条线的：

  • 2025 年初：「vibe coding」——命名了「全靠感觉、拥抱指数、忘掉代码长什么样」这种编程方式。
  • 2025 年底：「I've never felt this much behind as a programmer」——指出职业被「剧烈重构」，而重构发生在「比特」这一层。
  • 2026 年：转向「监督与理解」——这条最新推文是这条线索的自然终点。当产出被自动化，价值就转移到产出物的可理解性上，而「可理解性」是可以被提示词工程直接优化的。

换句话说，这条长推不是一堆小技巧，它是「后执行时代」的一份工作说明书。

08

边界与批判：什么时候这套方法会失效

一套好用的方法必须有明确的失效边界，否则就成了咒语。以下是几个可以实际检验的失效场景。

失效场景为什么失效退路
需要精确引用 视频和网页里的内容难以精确定位和引用；一旦要核对某个数字，必须回到原始来源 要求同时产出 Markdown 版本作为「事实底稿」
幻觉高发领域 越漂亮的产物越容易被当成「已经验证过」。视觉权威性会掩盖事实不确定性 强制要求标注来源链接与抓取时间；无来源的部分显式标为「未核实」
需要 diff 和版本管理 HTML 产物的 diff 体验远差于纯文本；5500 行的程序化动画更难 review 大产物要求同时保留可读的源文件（Manim/ECharts 源码优于渲染产物）
低带宽 / 无浏览器环境 L3、L4 都要求渲染能力；纯文本在任何设备上都能读 保持 L1 为默认，L3/L4 作为「需要时再生成」的升级
成本敏感的批量任务 L4 量级的任务动辄数美元、数小时（参见他 8 月那条 100 万 token 的推文） 按「这个知识点值不值 2 小时」来决定是否升到 L4

一个更诚实的表述：输出格式阶梯优化的不是「你懂了多少」，而是「你从一份 AI 产物里榨出多少理解」。它提高了理解密度，但没有提高事实密度——后者取决于模型本身和你的核查动作。这两件事经常被混为一谈。
